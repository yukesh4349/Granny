Project Snapshot & Guiding Principle
Core idea: “Don’t make the elderly adapt to the game. Make the game adapt to the elderly.” Granny is not 10
separate mini-games bolted onto an app — it is one continuous, voice-first world (Home → Market →
Journey → Music → Story → Garden → Album) wrapped around a memory-assistant companion that quietly
tracks accuracy, response time, mistakes and preferences, and reshapes future sessions around them.
What makes this different from a generic “brain training app”
•
Identity-preserving, not generic: games are populated with the user's own rooms, routines and
life-story, not stock puzzles.
•
Voice-first, not tap-first: speech is the primary input; large-touch UI is the fallback, not the other way
round.
•
Adaptive by design: a single difficulty engine drives every game and every companion interaction, not
per-game tuning.
•
Family-in-the-loop: caregivers get visibility and light co-play, without turning the app into a surveillance
tool.
•
Safety-first: distress detection and gentle escalation are architectural, not an afterthought bolted on
later.

model User {
  id              String   @id @default(uuid())
  role            Role     @default(ELDER)   // ELDER | CAREGIVER
  name            String
  phone           String?  @unique
  language        String   @default("en")
  familyGroupId   String?

  id         String   @id @default(uuid())
  userId     String
  type       String   // fact | anecdote | photo | routine
  content    String
  embedding  Unsupported("vector(1536)")?
  addedBy    String   // ELDER | CAREGIVER | SYSTEM
  createdAt  DateTime @default(now())
}

Backend master prompt
You are building the NestJS backend for "Granny", an AI cognitive-gaming and
memory-assistance app for elderly users. Stack: NestJS + TypeScript, Prisma ORM,
PostgreSQL, Redis (BullMQ for queues), WebSockets (Socket.IO gateway), Firebase
Admin SDK for push. This service NEVER calls the LLM directly — it proxies
conversation/voice calls to an internal FastAPI service at AI_SERVICE_URL.
Build these modules, each with controller + service + DTOs + Prisma repository:
1. auth        - phone/OTP + email login, JWT, roles ELDER/CAREGIVER, refresh tokens
2. users        - profile CRUD, family-group linking, consent flags
3. memory       - CRUD for Memory records; POST forwards new text/photo memories
   to the AI service for embedding, then stores the returned vector reference
4. games        - game catalog, start/end session, record attempts, fetch the
   next item's difficulty by calling the AI service's /difficulty/next endpoint
5. conversation - proxies voice/text turns to AI service /converse, persists
   the exchange + emotion label returned
6. reminders    - CRUD schedules, BullMQ cron jobs that fire FCM pushes + a
   WebSocket event the client turns into a spoken reminder
7. family        - caregiver dashboard read endpoints: adherence %, mood trend,
   last N game sessions, pending consent requests
8. safety        - receives distress flags from the AI service, fans out FCM
   alerts to the family group, logs an incident record
Cross-cutting requirements:
- Every ELDER-scoped endpoint must verify the caller owns the resource or is a
  linked CAREGIVER with explicit consent — write a reusable OwnershipGuard.
- All list endpoints paginated; all mutation endpoints validated with class-validator.
- Structured logging (pino) with request IDs; no PII in logs.
- Health check endpoint /health for Docker Compose readiness probes.
- Write Prisma schema exactly as in the provided blueprint, then generate migrations.
- Provide a docker-compose service block and a .env.example with every variable used.
Deliverable: a working NestJS app that boots with `docker-compose up`, exposes
Swagger docs at /docs, and passes a Jest test per module covering the happy path
and the ownership/consent guard rejection path.

Master Prompt — AI Microservice (FastAPI)
AI microservice master prompt
You are building the Python AI microservice for "Granny". Stack: FastAPI,
Pydantic v2, an LLM provider behind a thin adapter interface (so it can be
swapped), a vector store (pgvector via SQLAlchemy, or a managed vector DB),
a Whisper-based STT pipeline, and a TTS engine behind a similar adapter.
Endpoints to build:
1. POST /stt            audio bytes -> transcript + language + confidence
2. POST /tts             text + voice profile -> audio stream, natural pacing
3. POST /converse        { userId, text, sessionHistory } ->
   a) retrieve top-k relevant Memory embeddings for this userId
   b) run the emotion analyzer on the input text (+ optional audio features)
   c) build the system prompt from: persona template + retrieved memories +
      emotion state + safety rules (see safety notes below)
   d) call the LLM, return { reply, emotion, distressFlag, suggestedAction }
4. POST /memory/embed    text or image caption -> embedding vector, stored
   with metadata (userId, type, addedBy, timestamp)
5. POST /memory/search   userId + query -> top-k relevant memories (used by
   /converse internally and exposed for the family dashboard's search)
6. POST /difficulty/next { userId, gameKey, recentAttempts[] } -> next
   difficulty parameters (itemCount, delaySeconds, distractorCount) using an
   exponential moving average of accuracy + latency, clamped to 5 levels
7. POST /life-story/generate  (stretch) anecdote text -> a short narrated
   scene or 3-step choose-your-path script, scaffolded by cognitiveLvl
Persona & safety rules (bake into the system prompt template, not per-call):
- Warm, patient, never condescending; short sentences; no jargon.
- Never gives medical diagnoses or changes medication guidance — redirect to
  a family member or professional for anything clinical.
- Distress-phrase detector runs BEFORE the LLM call; on a match, skip normal
  generation and return a fixed gentle de-escalation script + distressFlag=true.
- Never invents facts about the user — only uses retrieved Memory records.
Non-functional requirements:
- Async endpoints throughout; STT/TTS calls streamed where the provider allows.
- Config via pydantic-settings reading from .env; no secrets in code.
- Structured JSON logging; redact transcript text at INFO level, full at DEBUG only.
- Dockerfile + inclusion in the shared docker-compose.yml on port 8000.
- Pytest coverage for the difficulty function and the distress-phrase detector,
  since those two are safety- and pedagogy-critical and must not regress silently.

You are building the shared Game Engine contract and all 10 cognitive games for
"Granny", to run inside the React web app (and later React Native). Games are
content, not separate engines — implement ONE TypeScript interface and 10
content modules that satisfy it.
interface CognitiveGame {
  key: string;
  title: string;
  primarySkills: string[];        // e.g. ['spatial-memory','visual-memory']
  startSession(userId, difficulty): SessionState;
  getNextItem(sessionState): GameItem;   // question/prompt + choices/targets
  submitAttempt(sessionState, response): AttemptResult; // correct, latencyMs, errorType
  endSession(sessionState): SessionSummary;
}
Implement all 10 using this contract, each in its own content module:
1. Remember My Home     - spatial+visual; place N objects in a room scene, hide,
   ask elder to point to where each object was.
2. Memory Market         - working memory+attention; show a 2-5 item shopping
   list, elder finds matching items in a virtual aisle grid.
3. Name & Face Match     - recognition+associative; introduce K character cards,
   later re-show faces and ask elder to say or pick the name.
4. Recipe Recall         - sequential+executive; show a step sequence, shuffle,
   elder reorders via drag or voice ("first we wash, then...").
5. Memory Journey        - episodic+sequential; a guided "walk" through N
   locations, then ask what was seen and in what order.
6. Complete the Tune     - auditory+associative; play a clip, elder names it or
   hums/says the next line (speech match against a phonetic reference).
7. Story Detective       - auditory+comprehension; TTS narrates a short story,
   then asks 2-3 comprehension questions.
8. Where Did I Keep It   - working+spatial; everyday objects placed around a
   home scene, delayed recall of locations.
9. Memory Garden         - visual+spatial+long-term; persistent user-built
   garden, later sessions test recall of prior placements (cross-session state).
10. Memory Album          - recognition+episodic; show a mix of seen/unseen
   images, elder identifies which they've seen and recalls details.
Shared requirements:
- Every game calls POST /difficulty/next after each session to get the next
  itemCount/delaySeconds/distractorCount — never hardcode difficulty curves.
- Every submitAttempt logs { correct, latencyMs, errorType } via the games
  module so the backend can persist Attempt rows.
- Voice-first: every prompt has a TTS narration and accepts a spoken response
  via STT, with large-button tap as a fallback for every interaction.
- Games 5, 9 and 10 must read from the user's own Memory records (real family
  photos, real places named by the caregiver) rather than stock content when available.
- Provide a GameWorldMap component: a single scrollable/explorable canvas that
  visually links Home -> Market -> Journey -> Music -> Story -> Garden -> Album
  as connected "rooms", not a grid of app icons.
Deliverable: the shared interface, all 10 content modules, unit tests for each
game's getNextItem/submitAttempt logic, and Storybook (or equivalent) entries
so each game can be visually reviewed in isolation.

Master Prompt — Web Frontend (React)
Web frontend master prompt
You are building the React web app for "Granny". Stack: React 18 + Vite +
TypeScript + Tailwind CSS + Zustand for state + the shared api-client package.
Audience: elderly users AND their caregivers, via role-based routing.
Design system constraints (non-negotiable, elderly-first accessibility):
- Minimum touch target 48x48px; primary actions 64px+.
- Base font size 20px+, high-contrast palette (WCAG AA minimum, aim for AAA on
  primary text), no light-grey-on-white text anywhere.
- Single-column layouts, max one primary action per screen, no hover-only
  affordances, no auto-advancing carousels.
- Every screen reachable within 2 taps/voice-commands from Home.
- A persistent large mic button is the primary way to interact; typed input
  is a secondary fallback, never the only path.
Screens to build, in this order:
1. Auth (phone/OTP) -> role-aware redirect (Elder Home vs Caregiver Dashboard)
2. Elder Home / GameWorldMap - the connected Home->Album world (Section 8)
3. Companion Chat - voice-first conversation view with waveform/listening state,
   large transcript text, gentle typing/thinking indicator
4. Reminders - today's schedule, one-tap "I took it" confirmation, gentle
   escalation UI if a reminder is repeatedly missed
5. Memory Album manager - upload/tag photos & anecdotes, consent toggle for
   what the companion is allowed to reference
6. Caregiver Dashboard - adherence chart, mood trend, recent game performance,
   pending consent/invite actions (reuse chart_display-style components)
7. Settings/Accessibility - text size, voice speed, language, contrast toggle
Technical requirements:
- api-client package wraps every backend call with typed request/response DTOs
  matching the NestJS DTOs — do not hand-roll fetch calls in components.
- WebSocket connection for live reminder pushes and companion streaming replies.
- Web Audio API for mic capture -> chunked upload to /conversation/voice.
- Route guards for ELDER vs CAREGIVER, redirecting unauthorized roles.
- i18n scaffold (even English-only at launch) so regional languages are a
  content swap, not a rewrite.
Deliverable: a working Vite app, Storybook for the design-system primitives,
and one Cypress/Playwright happy-path test per screen listed above.

10 Master Prompt — Mobile App (React Native /
Expo)
Mobile app master prompt
You are porting "Granny" to React Native (Expo, TypeScript). Reuse the
api-client and shared TypeScript types from packages/ — do not duplicate DTOs.
Priority order for mobile (do not try to port everything at once):
1. Voice companion chat (uses expo-av for mic capture, streaming playback)
2. Reminders with native push (expo-notifications + FCM) — this is the
   single highest-value mobile feature since it works even app-closed
3. ONE flagship game fully playable (recommend 'Where Did I Keep It' —
   simplest interaction pattern, easiest to validate touch-target sizing on)
4. Elder Home / world map (can reuse most layout logic from web via shared
   design tokens, but re-implement components natively for gesture quality)
5. Remaining games, family dashboard read-only view
Mobile-specific constraints:
- Respect OS-level accessibility settings (Dynamic Type / font scaling,
  reduce-motion) rather than fighting them.
- Offline-tolerant reminders: schedule locally via expo-notifications so
  medication alerts fire even without connectivity; sync confirmation on reconnect.
- Biometric or simple PIN unlock as an alternative to typing a password.
- Test on a physical low-cost Android device, not just iOS simulator — this is
  the device class most elderly users in India will actually own.
Deliverable: an Expo app that runs on `expo start`, with the reminder flow
and one flagship game fully functional end-to-end against the same backend
used by the web app.

11 Safety, Ethics & Accessibility Checklist
Before every demo or release, verify:
•
The companion never states or implies a medical diagnosis, and never suggests changing a dose or
schedule.
•
Distress phrases reliably trigger the de-escalation script in a manual test set of at least 20 phrases,
including indirect ones.
•
Every screen passes a 48px touch-target and WCAG AA contrast check.
•
Family/caregiver access to memories and location-like data requires explicit elder or guardian consent,
revocable at any time.
•
Voice recordings and health-adjacent data (medication logs) are encrypted at rest and in transit.
•
No dark patterns: no infinite scroll, no manipulative streaks, no guilt-based reminder copy.
•
A visible, one-tap path exists at all times to call a real family member or emergency contact.
